● Common idioms

  Yes — there are well-trodden patterns:

  - Google/Apple Maps: when a route is active, a tapped place's primary action
  becomes "Add stop." Appended before the destination by default. Reordering
  happens in a separate stops list with drag handles.
  - Waze: same — single "Add stop" action, stops list for reorder.
  - OsmAnd / Organic Maps (closest cousin to your app — power-user, no nagging):
   the slideout shows multiple actions: "Set as destination", "Add as 
  intermediate", "Set as start". They expose the position semantics directly
  instead of hiding them behind a generic "add."

  The OsmAnd pattern is the better fit for RoadTripRadar — you've already got a
  non-mainstream audience that wants control, not a single magic button.

  Recommendation tailored to your backtrack workflow

  Your workflow (drop destination, then backtrack pinning each turn closer to
  yourself) means each new pin should go right after your current location,
  pushing previous pins toward the destination. So the slideout's primary action
   wants to be "insert as next stop," not "append."

  Suggested slideout states:

  Existing waypoints: None
  Slideout actions (top → bottom): Navigate to (current behavior, becomes
    destination)
  ────────────────────────────────────────
  Existing waypoints: 1+
  Slideout actions (top → bottom): Insert as next stop (primary) · Append before
   
    destination · Replace destination · overflow: Replace specific stop / Set as

    start

  "Insert as next stop" matches your backtracking pattern as the one-tap
  default. "Append before destination" covers users who plan forward. "Replace
  destination" is the explicit override for the
  override-you-currently-get-by-accident.

  Stops list / route editor

  You'll also want a separate sheet — a stops list with drag-to-reorder, delete,
   and rename — accessible from a small "3 stops • Destination Name" chip pinned
   somewhere on the map (top bar, or above the speedometer-style HUD if you have
   one). That's the escape hatch when the in-slideout actions aren't enough
  (e.g., reordering after the fact, or removing a misplaced pin). This is also
  where you persist the route — extend PreferencesRepository to store an ordered
   List<Waypoint> instead of the four scalar poi_* keys, with single-waypoint as
   the degenerate case.

  What's worth deciding before planning

  A few choices that shape the implementation:

  1. Default primary action when a destination exists — "Insert as next stop"
  (matches your workflow) vs. "Append before destination" (matches Google Maps
  muscle memory). I'd pick the former since this is your app and your workflow
  is the design target.
  2. Max stops — soft limit (e.g., 25) or unbounded? Affects route line drawing
  perf.
  3. Per-stop labels — auto-named from POI/reverse-geocode, or prompt user, or
  both?
  4. Should the route line be a single multi-segment polyline through all stops,
   or distinct segments with different styling (e.g., solid for next leg, dashed
   for later legs)? The latter is nice on a wandering app.

  Want me to turn this into an implementation plan once you've weighed in on
  those?

● Two ways to handle "add past the destination"

  The semantic question is whether "destination" is a structural slot or just a
  label for the last stop:

  A. Demoting model (OsmAnd / Apple Maps): destination is privileged. Choosing
  "Set as new destination" pushes the new pin to the end of the list; the
  previous destination demotes to an intermediate stop. Route becomes current → 
  … → old-destination → new-pin.

  B. Flat-list model (Google Maps): no privileged slot. The last stop is just
  stops.last(). "Add stop" always appends; whichever pin happens to be last is
  "the destination."

  I'd recommend A for RoadTripRadar. Your users are deliberately picking a
  destination first — that intent shouldn't be silently reshuffled by a tap on a
   later pin. Making the demotion explicit ("Extend trip" / "Set as new
  destination") preserves their mental model and keeps the override visible.

  Slideout actions when waypoints exist

  ┌─────────────────────────────────┐
  │  POI name / address             │
  │  ─────────────────────────────  │
  │  ▶  Insert as next stop         │ ← primary; matches backtrack
  │  ▶  Insert before destination   │ ← Google-Maps "add stop"
  │  ▶  Extend trip past destination│ ← demotes old D to stop
  │  …  More                        │
  │      • Replace destination      │
  │      • Replace specific stop ▸  │
  │      • Set as start             │
  └─────────────────────────────────┘

  Three primary actions cover ~95% of intents; an overflow handles the rest.
  Middle-insertions (between stop 2 and stop 3 of a 5-stop trip) live in the
  stops-list editor, where dragging is more natural than picking from a menu.

  Wording matters here

  I'd avoid "Append" — it's vague about whether the old destination keeps its
  status. Concrete labels keep the consequence visible:

  - "Insert before destination" — old destination unchanged
  - "Extend trip past destination" — old destination demoted
  - "Replace destination" — old destination deleted

  If "Extend trip past destination" feels too long, "Continue past destination"
  is shorter and still unambiguous.

  Optional: visual route strip

  If three buttons feel cluttered, an alternative is a tiny vertical route
  preview inside the slideout with + insert-points between every pair of stops,
  including a + below the destination. Tap any + to drop the new pin there; tap
  an existing chip to replace. Self-explanatory, no labels to argue over, but
  more vertical space and more code. Worth considering only if the action-list
  version starts feeling crowded once you build it.

  Want me to draft an implementation plan around the action-list approach (model
   1: demoting destination, three primary actions + overflow, separate
  stops-list editor)?

● On the reorderable list dependency

  There's no first-party Compose reorderable list. The honest landscape:

  - androidx.recyclerview.widget.ItemTouchHelper — built into the SDK and
  battle-tested, but it's a View-system helper. Using it from Compose means
  wrapping a RecyclerView inside AndroidView, which means hand-bridging
  adapters, view holders, and state. Lots of code, awkward, and you give up
  Compose's recomposition model for that one screen. Not worth it for a stops
  list.
  - Compose Material3 / Foundation — neither has a ReorderableLazyColumn.
  There's an open issue at AOSP asking for one. As of now, nothing built-in.
  - sh.calvin.reorderable (Calvin Liang, MIT) — single contributor but actively
  maintained (last release within the last few months at the time of writing),
  small (~50 KB), Compose-native API (ReorderableItem wrapping LazyColumn
  items). Used by a number of FOSS projects. Honest about its limits in the
  README. Trust profile: small library, single maintainer, no
  Anthropic/Google/JetBrains backing — same risk class as most Compose-ecosystem
   tools right now.
  - org.burnoutcrew.composereorderable — was the de-facto standard, last update
  ~2022. Probably stale; I'd avoid.
  - DIY in Compose — Modifier.pointerInput { detectDragGesturesAfterLongPress }
  + LazyListState, tracking per-item offset and animating displaced items, plus
  auto-scroll near edges. Realistically 200–300 lines for the polished version.
  No new dependency, full control, and the surface area is contained because
  waypoint lists are short (rarely >20 items).

  Given your "prefer SDK / high trust" stance and the modest list size, I'd 
  recommend DIY. The implementation isn't trivial but it's bounded, no
  third-party trust required, and a stops list is a simple enough surface that
  the polish ceiling matches what we'd want anyway. If during implementation it
  grows hairier than expected (fast-drag jitter, edge auto-scroll), we can
  switch to sh.calvin.reorderable as an isolated change — the call sites are
  localized to one Composable.
